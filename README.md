# SR-Output

SAP ERP 서비스지원팀의 **SR(Service Request) 산출물 초안 작성 에이전트** 저장소.
SR 1건을 접수해 FP내역서 · FD · TD · 테스트결과서 4종 산출물의 초안을 자동으로 작성하는
Claude Code 오케스트레이터 파이프라인을 관리함.

## 저장소 구조

```
SR-Output/
├── AGENTS.md              # 팀 구성 · 워크플로우 · 위임 규칙 등 오케스트레이터 시스템 프롬프트(CLAUDE.md 역할)
├── prompt/
│   └── sr_output.md       # SR 처리 실행 프롬프트 (사용자가 직접 실행하는 진입점)
└── reference/             # 산출물별 작성 가이드 (AGENTS.md·prompt에서 참조)
    ├── prompt-guide.md        # 팀원 위임용 프롬프트 8섹션 표준
    ├── fp-guide.md             # FP내역서(공수산정서) 작성 가이드
    ├── fd-guide.md             # FD(기능설계서) 작성 가이드
    ├── td-guide.md             # TD(기술설계서) 작성 가이드
    └── test-result-guide.md    # 테스트결과서 작성 가이드
```

실행 시 로컬에만 존재하는 폴더(저장소에는 포함하지 않음):

| 폴더 | 용도 |
|------|------|
| `prep/{SR NO}/` | SR별 입력 자료(zdown 수정 전 · 후 html, 기존 FD · TD 문서) — 사용자가 미리 준비 |
| `template/` | FP · FD · TD · 테스트결과서 서식 기준 참고 파일 — 사용자가 미리 준비 |
| `result/{SR NO}/` | 산출물 4종의 최종 저장 위치 — 에이전트가 실행 중 생성 |

## 파일별 역할

### `AGENTS.md`
오케스트레이터(클로니)와 팀원 5명(SR 분석가 · ABAP 소스분석가 · 공수산정 담당 · 기능설계자 · QA 테스터)의
프로파일 · 성향 · 경력, SR 처리 4단계 워크플로우, 팀원 위임 규칙(계층형 · 파이프라인형 · 토론형 · 협업형),
대화 · 마크다운 작성 가이드, 정직한 보고 규칙, 그리고 실행 중 얻은 시행착오를 담은 `Lessons Learned`를 정의함.
모든 에이전트 실행 전에 필수로 참고하는 최상위 규칙 문서임.

### `prompt/sr_output.md`
사용자가 SR 번호 하나만 입력하면 실행되는 표준 프롬프트. `[목표]/[역할]/[맥락]/[입력]/[처리]/[출력]/
[제약조건]/[예시]` 8섹션 표준(`reference/prompt-guide.md`)을 따라 작성됨. SR 분석 → 소스 전후 비교 분석
→ 산출물 4종 병렬 작성 → 검수 · 통합의 4단계 처리와 완료조건을 정의함.

### `reference/*.md`
산출물 4종 각각의 서식 · 파일명 규칙 · 필수 입력자료 · 편집 방법(PowerShell + Office COM)을 담은
작성 가이드. `prompt-guide.md`는 산출물 가이드가 아니라, 팀원에게 위임하는 프롬프트 자체를 작성할 때
따르는 표준임.

## SR 처리 워크플로우

| 단계 | 작업 | 담당 | 출력 |
|------|------|------|------|
| 1 | SR 분석 | SR 분석가 | 구조화된 SR 요약본 |
| 2 | 소스 전후 비교 분석 | ABAP 소스분석가 | 비교 분석 결과(차이점 · 비즈니스적 의미) |
| 3 | 산출물 초안 작성(4종 병렬) | 공수산정 담당 · 기능설계자 · ABAP 소스분석가 · QA 테스터 | FP내역서 · FD · TD · 테스트결과서 |
| 4 | 검수 · 통합 | 오케스트레이터 | 공통 필드(SR NO · 모듈 · 프로그램ID) 정합성 확인 완료된 최종 산출물 |

자세한 규칙은 `AGENTS.md`의 `## SR 처리 워크플로우`, `## 팀원 위임 규칙` 참고.

## 사용 방법

1. SR별 입력 자료를 `prep/{SR NO}/`에 준비함(zdown 수정 전 · 후 html 필수, 기존 FD · TD 문서는 선택).
2. Claude Code에서 `prompt/sr_output.md`를 실행하고 SR 번호를 입력함.
3. `result/{SR NO}/`에 생성된 산출물 4종을 확인함.

## 프롬프트 · 가이드 버전 관리(일자별)

이 저장소는 SR 산출물 초안 작성 에이전트의 프롬프트(`prompt/sr_output.md`)와 규칙 문서(`AGENTS.md`,
`reference/*.md`)를 **동일 파일을 계속 갱신하는 방식**으로 운영하며, 일자별 변경 이력은 아래 두 지점에서
관리함.

- **작업 브랜치**: 세션(작업일)마다 `YYYY.MM.DD` 형식의 브랜치에서 작업함(예: `2026.09.10`). 브랜치명
  자체가 해당 작업일을 나타내므로, 특정 날짜에 어떤 변경이 있었는지는 그 날짜의 브랜치를 확인하면 됨.
- **커밋 이력**: 브랜치 내에서도 파일별 변경 시점은 git 커밋 이력으로 추적함. 특정 파일이 날짜별로 어떻게
  바뀌었는지 확인하려면 아래 명령을 사용함.

```bash
# 특정 파일의 일자별 변경 이력(이름 변경 포함) 확인
git log --follow --date=short --format='%ad %h %s' -- prompt/sr_output.md

# 특정 날짜에 변경된 파일 전체 확인
git log --since="2026.09.10" --until="2026.09.11" --name-only

# 두 시점 사이의 프롬프트 · 가이드 변경 내용(diff) 확인
git diff <이전 커밋 또는 날짜> <이후 커밋 또는 날짜> -- prompt/ AGENTS.md reference/
```

신규 작업일에 프롬프트나 가이드를 수정할 때는 다음을 지킴.

- 새 브랜치(`YYYY.MM.DD`)를 만들어 작업하고, 해당 브랜치에서 커밋 · 푸시함.
- 커밋 메시지는 변경 대상 파일이 드러나도록 작성함(예: `Update sr_output.md`, `Update fp-guide.md`).
- 반복 검증된 교훈은 임시 기록에 머물지 않고 `AGENTS.md`의 `## Lessons Learned`에 승격하여, 다음 작업일에도
  동일한 시행착오를 반복하지 않도록 함.

## 마크다운 작성 규칙

이 저장소의 모든 문서(`AGENTS.md`, `prompt/`, `reference/` 포함)는 아래 스타일을 따름
(`AGENTS.md`의 `## 마크다운 작성 가이드` 참고).

- 명사체 종결어미 사용(예: "~한다" → "~함")
- 한 줄 120자 이내, 긴 문장은 적절히 줄바꿈
- 빈 줄 없이 줄바꿈할 경우 줄 끝에 스페이스 2개 필수
- 취소선 오인을 막기 위해 `~`는 앞뒤에 스페이스를 붙여 ` ~ `로 표기
